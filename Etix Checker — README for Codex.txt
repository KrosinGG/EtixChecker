Etix Checker — README for Codex
1. Цели проекта (Project Goals)
Etix Checker — это асинхронный инструмент автоматизации на Python, предназначенный для:
параллельной проверки доступности билетов на сайтах Etix-подобной архитектуры;
попытки выбрать билеты и добавить их в корзину через множество вкладок;
устойчивой работы через прокси (включая CAPTCHA и деградацию прокси);
корректного восстановления работы после краша (crash-safe resume);
формирования детерминированного CSV-отчёта (report.csv), пригодного для дальнейшей фильтрации и аналитики.
Проект ориентирован на стабильность, повторяемость и масштабирование, а не на разовый парсинг.
2. Архитектура проекта (Architecture Overview)
2.1. Точка входа
cli.py
Консольный интерфейс (меню запуска).
Детект незавершённого прогона.
Выбор: resume / fresh.
Live-прогресс через rich.Live.
Делегирует всю бизнес-логику в app_core.check_shows().
2.2. Ядро приложения
app_core.py — единственный источник бизнес-логики.
Ключевые зоны ответственности:
чтение входных CSV (shows.csv, Chezile.csv);
управление прокси-пулом (good / bad / captcha-blocked);
запуск Playwright (Chromium, async);
создание browser contexts (1 прокси = 1 контекст = 1 вкладка);
обработка каждого шоу;
crash-safe resume (runs + checkpoint);
формирование строк отчёта и запись report.csv.
2.3. Данные и файловая структура
data/
 ├─ shows.csv        # список шоу (url + параметры)
 ├─ Chezile.csv      # прокси
 ├─ bad_proxies      # прокси, помеченные как плохие
 ├─ good_proxies     # проверенные хорошие прокси
 └─ human.yml        # human-like настройки (используются ядром)

runs/
 └─ <run_id>/
     ├─ params.json
     └─ checkpoint.json

3. Принцип работы (Execution Model)
3.1. Общий workflow
CLI проверяет shows.csv.
CLI определяет:
есть ли незавершённый прогон;
можно ли безопасно сделать resume (fingerprint совпадает).
Запуск check_shows():
инициализация RunContext;
загрузка прокси и шоу;
запуск браузера и вкладок.
Для каждого шоу:
перенос pending → inflight;
попытки добавления билетов во всех вкладках;
CAPTCHA-ретраи при необходимости;
формирование строки результата;
commit_done() (атомарно).
После всех шоу:
запись report.csv;
удаление checkpoint;
закрытие браузера.
3.2. Crash-safe resume
Ключевая сущность — RunContext:
checkpoint.json содержит:
очереди pending / inflight / done;
уже готовые строки отчёта;
fingerprint входного shows.csv.
Правила:
если checkpoint существует → прогон считается незавершённым;
resume возможен только при совпадении fingerprint;
при успешном завершении checkpoint удаляется;
done-строки всегда подхватываются при resume.

4. Формирование результата (Report Logic)
4.1. Оценка доступности
success_carts — количество вкладок, где корзина успешно набрана.
per_order_limit — лимит билетов за заказ.
estimated_available_>= = success_carts * per_order_limit.
Это минимальная гарантированная оценка, не точное число.

4.2. Статусы (логика)
OK
если target_total задан и estimated_available_>= >= target_total;
или если набрано минимально нужное число корзин.
SOLD OUT
ENDED
КРАСНАЯ ЛИНИЯ (билетов не хватает)
ЧАСТИЧНО (есть успехи, но цель не достигнута)

4.3. Структура строки отчёта (INVARIANT)
name
url
target_total
site_per_order_limit
per_order_limit
tabs_used
attempts
success_carts
estimated_available_>=
needed_carts
status
ok_all
inv_errors
other_fails
notes

⚠ Формат report.csv — жёсткий инвариант.

5. Инварианты (DO NOT BREAK)
Codex не должен нарушать следующие правила:
5.1. Данные и формат
структура report.csv;
смысл и вычисление estimated_available_>=;
названия и значения статусов;
порядок колонок.

5.2. Resume-механика
checkpoint.json — единственный источник состояния;
логика pending / inflight / done;
resume запрещён при изменении shows.csv.
5.3. Прокси-логика
плохие прокси → bad_proxies;
CAPTCHA ≠ bad proxy (captcha-blocked ≠ banned);
один прокси не может быть в двух вкладках одновременно.
5.4. CLI-контракт
callback on_show_done(row, done_idx, total) должен работать;
live-прогресс Rich не должен ломаться.
6. Safe Refactor Zones (Где можно улучшать)
Codex может безопасно работать в следующих зонах:

✅ Разрешено
улучшение эвристик выбора прокси;
оптимизация CAPTCHA-retry логики;
улучшение детекта SOLD OUT / ENDED;
добавление логов и метрик;
ускорение или стабилизация Playwright-действий;
улучшение устойчивости к таймингам/лагам сайта.

❌ Запрещено
изменение формата report.csv;
удаление или упрощение crash-safe resume;
отказ от очередей pending / inflight / done;
изменение семантики статусов;
“умный рефакторинг”, который переписывает всё ядро.

7. Checklist тестов (Smoke-Run Checklist)
Перед любыми изменениями обязательно:

7.1. Базовый прогон
 shows.csv из 1–2 URL
 TABS_COUNT = 2
 корректно создаётся report.csv

7.2. Resume
 остановить скрипт на середине;
 перезапустить → resume продолжается;
 после завершения checkpoint удалён.

7.3. Прокси
 плохой прокси уходит в bad_proxies;
 CAPTCHA-прокси не банится;
 вкладки заменяются корректно.

7.4. Статусы
 SOLD OUT → корректный статус + скрин;
 OK → верная оценка estimated_available_>=;
 ЧАСТИЧНО → без ложного OK.

7.5. CLI
 live-прогресс обновляется;
 строки появляются по мере обработки;
 нет падений при отсутствии Rich.

8. Ключевая философия проекта
Etix Checker — это не парсер, а устойчивый автоматизированный процесс.
Любые улучшения должны:
сохранять воспроизводимость;
быть crash-safe;
не ломать downstream-аналитику (CSV).
Если хочешь, следующим шагом я могу:
подготовить ARCHITECTURE.md с диаграммами потоков,
или сделать Codex-prompt “Allowed / Forbidden Changes” в кратком виде,
или собрать template для regression-тестов под будущие изменения.
